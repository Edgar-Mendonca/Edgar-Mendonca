# How Edgar works

## Environment

Windows, PowerShell, Python virtual environments and pip, VS Code, GitHub repositories and GitHub Pages, and AI
coding agents. Installation steps should be explicit and match that setup. Tailwind CSS is a strong preference for
websites, with established libraries (DaisyUI, Bootstrap, AOS, Swiper, GSAP) over piles of custom CSS. Science work
uses NumPy, SciPy, pandas, Matplotlib, Seaborn, Plotly and PyMuPDF; browser charts have used Chart.js and ECharts.

## Preferences that depend on the job

Browser access and easy sharing matter, and so does real scientific capability; desktop apps, Rust, Tauri and
bundled runtimes are welcome when they make an app more capable or easier to install. Separate repositories per app,
open-source licences, version control, automatic updates and free hosting are recurring goals.

## Working patterns

1. Practical outputs: an actual file, app, prompt, tracker or finished visual rather than only a discussion.
2. Iterative correction: screenshots, logos, layouts and wording refined through direct corrections.
3. Technical substance and presentation together: correct calculations and standards, readable charts and tables,
   consistent branding.
4. Workflow thinking: how a tool is installed, updated, hosted, exported, shared and used in real work.
5. Integration: separate ideas converge into one family or workflow.
6. Scientific strength: a simple demo is not enough where real analysis is expected.
7. Accessibility: browser access, mobile behaviour and downloadable documents.
8. Direct feedback: wrong colours, logos, missing functions and incomplete chapters are named plainly.
9. Continuity: "next", "same" and "continue" refer to the established workflow.
10. Keep what is approved: when one thing is corrected, everything else stays as it was.
11. Context-specific scope: a general reference stays general when asked.
12. Learning through use: practical work comes with the underlying concepts and mathematics.

## How an assistant should help

Turn requests into usable deliverables; supply the file format asked for, with a working link; give coding agents
concrete prompts with scope and acceptance criteria; preserve existing work; continue long workflows without losing
context; and read the actual current file before describing or editing it.

In engineering: separate observations, proposed causes, calculated checks and verified results; use the actual
standard edition and project documents; never treat a database flag as a sour-service qualification; never invent
missing measurements; show units, assumptions and the calculation; and never claim a test passed or a design is safe
without evidence.

In design: clean interfaces with established libraries, the correct colours and logos, mobile layouts, a useful home
page, and project-specific exclusions applied only to their own project.

In explanations: the mathematics when asked, explicit setup steps, clear distinctions between build tools, front-end
libraries, back-end services, hosting and storage, and no polished descriptions hiding unfinished prototypes.
